# Hi-fi_store

Интернет-магазин hi-fi техники: усилители, акустика, проигрыватели, кабели.

## Стек

- **Бэкенд:** ASP.NET Core Web API на .NET 10, EF Core, PostgreSQL, ASP.NET Core Identity.
- **Фронт:** Next.js (App Router) + TypeScript + Tailwind (папка `web/`).

## Структура

```
api/
  HiFiStore.slnx
  src/
    HiFiStore.Api/             контроллеры (витрина, корзина и заказы, аккаунт, админка), разбор параметров,
                               команды migrate и create-admin (Cli/), Program.cs
    HiFiStore.Domain/          сущности каталога и заказов
    HiFiStore.Infrastructure/  EF Core, миграции, сервисы каталога, заказов и админки, Identity-инициализация, тестовые данные
  tests/
    HiFiStore.Tests/           unit- и интеграционные тесты
web/                           витрина на Next.js (главная, каталог, карточка товара, корзина, оформление заказа, вход,
                               личный кабинет, страницы для покупателей /info/*) и админ-панель (/admin), см. web/README.md
docker-compose.yml             PostgreSQL для локальной разработки
```

## Локальный запуск

Нужны .NET 10 SDK, Node.js 20+ и Docker.

```bash
docker compose up -d                      # PostgreSQL на localhost:5432 (postgres/postgres, БД hifistore)

cd api
export ConnectionStrings__Store='Host=localhost;Port=5432;Database=hifistore;Username=postgres;Password=postgres'
export Seed__Admin__Email='admin@example.local'      # необязательно: создаёт администратора при Store:AutoMigrate
export Seed__Admin__Password='<пароль для локальной разработки>'
dotnet run --project src/HiFiStore.Api    # в Development миграции применяются и заполняется демо-каталог
```

API слушает `http://localhost:5166`, OpenAPI-описание доступно в Development по `/openapi/v1.json`.

Пароли и строку подключения задавайте через переменные окружения или `dotnet user-secrets`,
а не в `appsettings*.json`. Значения из примера годятся только для локальной разработки.

### Демо-каталог

В Development (`Store:DemoCatalog`) API при старте заполняет каталог тестовыми данными из
`api/src/HiFiStore.Infrastructure/Persistence/Seeding/DemoCatalog.cs`: разделы с характеристиками, вымышленные бренды
(Aurora, Nord Audio, Kvarts, Vega, Liniya) и товары с описаниями на украинском, как и витрина по умолчанию.
У каждого опубликованного товара три иллюстрации (общий вид, деталь, в интерьере) из `web/public/demo/products` —
это нарисованные заглушки, их генерирует `node web/scripts/demo-images.mjs`; настоящие фото задаются в админке.
В уже заполненной базе (например, на демо-сайте) API при старте с `Store:DemoCatalog` заменяет у демо-товаров
старые заглушки placehold.co этими иллюстрациями; фото, заданные вручную, не трогает.
На странице товара под описанием — блок «Матеріали від майстра» (огляд з відео, підключення, догляд, питання,
відгуки) с плашкой «Демо»: тексты-шаблоны по типу товара из `web/lib/demo-content.ts`, видео — заглушка плеера.
Так выглядит задуманное наполнение, пока у материалов нет модели данных и ТЗ.
Каталог заполняется, только если в базе ещё нет ни одного товара, поэтому уже заполненная база разработки сама
не обновится (например, в ней останутся прежние русские тексты). Чтобы пересоздать каталог, удалите базу разработки
и снова запустите API в Development — миграции и демо-каталог применятся заново:

```bash
cd api
dotnet tool restore
dotnet ef database drop --force --project src/HiFiStore.Infrastructure --startup-project src/HiFiStore.Api
dotnet run --project src/HiFiStore.Api
```

Вместо `dotnet ef database drop` можно `docker compose exec db dropdb -U postgres --force hifistore`. Вместе с базой
удаляются пользователи и заказы; администратор из `Seed__Admin__*` создаётся заново при старте.

## Миграции

Миграции лежат в `api/src/HiFiStore.Infrastructure/Persistence/Migrations`. В Development они
применяются при старте (`Store:AutoMigrate`). Новую миграцию добавляйте так:

```bash
cd api
dotnet tool restore
dotnet ef migrations add <Имя> --project src/HiFiStore.Infrastructure --startup-project src/HiFiStore.Api --output-dir Persistence/Migrations
```

Строка подключения для `dotnet ef` берётся из `ConnectionStrings__Store`, как и при запуске.

Роли `Admin` и `Customer` тоже создаёт миграция (`SeedIdentityRoles`, постоянные идентификаторы), а не код при старте.
Поэтому в окружении без `Store:AutoMigrate` достаточно применить миграции, и регистрация сразу назначает роль `Customer`.
Применить миграции без запуска API можно командой самого API (SDK и `dotnet ef` для неё не нужны, см.
[развёртывание](#развёртывание-в-продакшене)) или через `dotnet ef`:

```bash
cd api
dotnet run --project src/HiFiStore.Api -- migrate
dotnet ef database update --project src/HiFiStore.Infrastructure --startup-project src/HiFiStore.Api   # то же самое
```

Если роли в базе уже были созданы при старте прежней версией (со случайными идентификаторами), миграция переводит их
на постоянные вместе с пользователями.

## Развёртывание в продакшене

В продакшене (`ASPNETCORE_ENVIRONMENT=Production`, по умолчанию) `Store:AutoMigrate` выключен: при старте API
не трогает схему базы и не создаёт пользователей. Для этого у исполняемого файла API есть команды обслуживания —
они используют ту же конфигурацию, но веб-сервер не запускают. На сервере нужен только ASP.NET Core Runtime 10,
SDK и `dotnet ef` не нужны.

1. Соберите и опубликуйте API:

   ```bash
   cd api
   dotnet publish src/HiFiStore.Api -c Release -o publish      # папка api/publish в .gitignore
   ```

   Содержимое `api/publish` скопируйте на сервер. Команды ниже запускайте из этой папки — там лежат `appsettings.json`.

2. Задайте строку подключения (и при необходимости адрес, на котором слушать) через переменные окружения —
   не в `appsettings*.json`:

   ```bash
   export ConnectionStrings__Store='Host=db.internal;Port=5432;Database=hifistore;Username=hifistore;Password=…'
   export ASPNETCORE_URLS='http://0.0.0.0:8080'
   ```

3. Примените миграции — схема, последовательность номеров заказов, роли `Admin` и `Customer`:

   ```bash
   dotnet HiFiStore.Api.dll migrate
   ```

   Команда показывает, какие миграции применяет, и завершается. Если базы ещё нет, она будет создана
   (у пользователя БД должно быть право на это; иначе создайте пустую базу заранее). Повторный запуск безопасен.
   Запускайте `migrate` при каждом обновлении, до старта новой версии.

4. Создайте администратора:

   ```bash
   dotnet HiFiStore.Api.dll create-admin --email admin@example.com
   ```

   Пароль в аргументах не передаётся (он остался бы в истории команд). В терминале команда спросит его дважды со
   скрытым вводом. Для автоматизации задайте переменную `HIFISTORE_ADMIN_PASSWORD`, например из менеджера секретов:
   `HIFISTORE_ADMIN_PASSWORD="$(cat /run/secrets/admin_password)" dotnet HiFiStore.Api.dll create-admin --email …`.
   Пароль проверяется теми же правилами Identity, что и при регистрации (не короче 8 символов, цифра, строчная
   и заглавная буквы, спецсимвол); ошибки выводятся, и пользователь не создаётся.

   - Новый пользователь создаётся с подтверждённым email и ролью `Admin`.
   - Если пользователь с таким email уже есть, ему выдаётся роль `Admin`, а пароль не меняется и не запрашивается.
   - `--reset-password` задаёт существующему пользователю новый пароль и снимает блокировку входа после
     неудачных попыток — так восстанавливается доступ, если пароль администратора забыт.
   - Где команду не запустить (бесплатный Render без shell), при `Store:AutoMigrate` можно задать новый пароль
     в `Seed__Admin__Password` и добавить `Seed__Admin__ResetPassword=true`: при старте API сменит пароль
     администратору `Seed__Admin__Email` и снимет блокировку. Пароль меняется, только если отличается от текущего,
     так что повторные старты сессии не сбрасывают; после входа флаг лучше убрать.
   - Пока в базе есть неприменённые миграции, команда ничего не делает и просит сначала выполнить `migrate`.

5. Запустите API:

   ```bash
   dotnet HiFiStore.Api.dll
   ```

   и войдите администратором: на сайте — через `/login` (в шапке появится ссылка на админ-панель `/admin`) или
   через `POST /api/auth/login` — `/api/admin/...` доступны с полученным токеном.

Коды выхода команд: `0` — успех, `1` — ошибка выполнения (нет строки подключения или пароля, база недоступна,
не применены миграции, некорректный email, пароль не прошёл проверку), `2` — неизвестная команда или неверные
аргументы (выводится справка, её же показывает `dotnet HiFiStore.Api.dll --help`). Аргументы, начинающиеся с `-`
(например, `--urls`), как и раньше относятся к запуску API. В разработке те же команды доступны через
`dotnet run --project src/HiFiStore.Api -- migrate` и `… -- create-admin --email …`.

## Почта

Это основа магазина без согласованного ТЗ, домена и почтового аккаунта. По умолчанию
в `appsettings.json` выбран `Email:Provider=Log`: письма **не отправляются**, их адрес, тема и текст
со ссылками выводятся в журнал API для демонстрации. Домен и учётная запись сервиса для этого не нужны.

Готовые клиентские события: подтверждение email после регистрации, восстановление пароля,
принятие заказа, смена статуса заказа и подтверждение заявки на консультацию (если оставлен email).
Письма на украинском, у каждого текстовая и HTML-версия. Уведомления владельцу в мессенджерах пока не реализованы;
существующие письма владельцу отправляются только при заполненном `Store:OwnerEmail`.

### Подключение реальной отправки позднее

Транспорт отделён интерфейсом `IEmailTransport`. В комплекте — Log, HTTP API Resend и SMTP.
Бесплатный Render блокирует исходящие порты 25, 465 и 587, поэтому для него предусмотрен Resend через HTTPS:
[ограничения Render](https://render.com/docs/free#other-limitations).
У тестового домена `resend.dev` есть ограничения на получателей; для отправки клиентам нужен подтверждённый
домен отправителя: [документация Resend](https://resend.com/docs/knowledge-base/403-error-resend-dev-domain).
Покупать домен или создавать аккаунт для текущего шаблона не требуется.

Когда будут домен и настройки заказчика:

1. Подтвердите домен отправителя в Resend с DNS-записями, которые выдаст сервис.
2. Создайте ключ с правом отправки и задайте **в секретах окружения API**, не в Git:

| Переменная | Описание |
| --- | --- |
| `Email__Provider` | `Resend` для отправки, `Log` для демонстрации |
| `Email__Resend__ApiKey` | Секретный ключ Resend с правом отправки |
| `Email__From` | Адрес на подтверждённом домене, например `notifications@shop.example` |
| `Email__FromName` | Имя магазина (по умолчанию Hi-Fi Store) |
| `Email__ReplyTo` | Необязательный рабочий email для ответов покупателей |
| `Store__PublicUrl` | Адрес витрины для ссылок в письмах, например `https://hifistore-web.onrender.com` (по умолчанию `http://localhost:3000`) |
| `Store__OwnerEmail` | Куда присылать новые заказы и заявки на консультацию; пусто — владельцу не пишем |

3. Проверьте доставку на согласованный тестовый адрес до включения писем клиентам.
   Успешный ответ сервиса означает приём письма к отправке; попадание во входящие проверяется отдельно.

Для другого сервиса достаточно добавить реализацию `IEmailTransport`. Существующий SMTP включается
через `Email__Provider=Smtp`, `Email__From`, `Email__Smtp__Host`, `Email__Smtp__Port` (587),
`Email__Smtp__Username`, `Email__Smtp__Password`, `Email__Smtp__EnableSsl` (true).
Порт 465 (неявный TLS) встроенным SMTP-клиентом не поддерживается.
`Auto` выбирает Resend при наличии его ключа, иначе SMTP при наличии Host, иначе Log.
В шаблоне явный `Log` имеет приоритет: одного добавления ключа недостаточно, чтобы начать рассылку.
Выбранный реальный транспорт с неполными настройками вызывает понятную ошибку при старте, без тихого перехода в Log.

Очередь работает в памяти процесса: медленный сервис не задерживает запрос покупателя.
Сетевые ошибки, тайм-ауты, 429 и 5xx повторяются дважды; постоянные ошибки Resend (например, 401/403/422) не повторяются.
Повторные запросы одного письма используют один `Idempotency-Key`, чтобы не продублировать его при сетевом сбое:
[Resend — idempotency keys](https://resend.com/docs/dashboard/emails/idempotency-keys).
Неотправленные письма теряются при остановке API; для рабочего магазина нужна сохраняемая очередь,
мониторинг отказов и проверка доставляемости. Тела ошибок провайдера и секретный ключ в журнал не выводятся.

### Ссылки и перезапуски

Ссылки из писем ведут на страницы витрины `/confirm-email` и `/reset-password`, которые сами вызывают
`/api/auth/confirmEmail` и `/api/auth/resetPassword`. Коды в ссылках защищены ключами ASP.NET Core Data Protection:
ключи сохраняются в PostgreSQL в таблице `DataProtectionKeys` (миграция `PersistDataProtectionKeys`,
имя приложения `HiFiStore`). Новые ссылки и bearer-токены переживают перезапуск контейнера.
Старые ссылки и сессии от версии с файловыми ключами потребуют повторной выдачи один раз при переходе на БД.
Ключи в таблице не шифруются отдельным сертификатом: доступ к этой таблице и резервным копиям должен быть закрыт,
а для рабочего окружения предусмотрите защиту ключей при хранении.

## Тесты

```bash
cd api
dotnet test                                                       # unit-тесты: разбор параметров и команд, slug, заказы, модель EF
HIFISTORE_TEST_CONNECTION='Host=localhost;Port=5432;Database=hifistore_test;Username=postgres;Password=postgres' \
  dotnet test                                                     # + интеграционные тесты с PostgreSQL
```

Интеграционные тесты пересоздают базу из `HIFISTORE_TEST_CONNECTION` и заполняют её демо-каталогом.
Без этой переменной они пропускаются, а не проходят молча. Используйте отдельную базу, не рабочую.
Тесты заказов создают собственные товары, поэтому списание остатков не влияет на тесты каталога.

## CI

GitHub Actions (`.github/workflows/ci.yml`) запускается на push в `main` и на каждый pull request в любую ветку,
так что проверяются и PR, открытые поверх других PR. Новый запуск для той же ветки или PR отменяет предыдущий.

- **`api`** — .NET 10 в `api/`: `dotnet restore`, `dotnet build -c Release`, `dotnet test -c Release`.
  PostgreSQL 17 поднимается service-контейнером, `HIFISTORE_TEST_CONNECTION` указывает на него, поэтому
  интеграционные тесты выполняются. Если хотя бы один тест пропущен (Skipped), job падает.
- **`web`** — Node.js 22 в `web/`: `npm ci`, `npm run lint`, `npm run build`. Запущенный API для сборки не нужен.

## API

| Метод и путь | Описание |
| --- | --- |
| `GET /api/catalog/categories` | Дерево разделов |
| `GET /api/catalog/products` | Товары с фильтрами, сортировкой и пагинацией |
| `GET /api/catalog/products/{slug}` | Карточка опубликованного товара |
| `GET /api/catalog/facets?category=` | Значения и диапазоны для построения фильтров |
| `POST /api/auth/register`, `POST /api/auth/login`, `POST /api/auth/refresh` | Identity: регистрация и вход по bearer-токену; новый пользователь получает роль `Customer` |
| `GET /api/account/me` | Текущий пользователь, роли и `emailConfirmed` (нужен токен) |
| `GET /api/auth/confirmEmail`, `POST /api/auth/resendConfirmationEmail` | Identity: подтверждение email по ссылке из письма, повторная отправка письма |
| `POST /api/auth/forgotPassword`, `POST /api/auth/resetPassword` | Identity: письмо со ссылкой и новый пароль. Письмо уходит только на **подтверждённый** email; ответ `200` в любом случае |
| `POST /api/cart/quote` | Пересчёт корзины по каталогу: актуальные цены, наличие, итог |
| `POST /api/orders` | Оформление заказа; гостем или с bearer-токеном (тогда заказ привязывается к аккаунту) |
| `GET /api/orders/by-token/{token}` | Заказ по публичному токену со страницы подтверждения |
| `GET /api/account/orders`, `GET /api/account/orders/{id}` | Заказы текущего пользователя, новые сверху (нужен токен; чужой заказ — `404`) |
| `/api/admin/...` | Управление каталогом и заказами, только для роли `Admin` — см. [ниже](#административный-api) |

Списки заказов принимают `page` и `pageSize` (1–100, по умолчанию 20).

Параметры списка товаров:

- `category` — slug раздела, включает вложенные разделы;
- `brand`, `condition` (`new`, `used`, `demo`) — несколько значений через запятую или повтором параметра;
- `minPrice`, `maxPrice`, `inStock=true`, `q` — цена, наличие, поиск по названию;
- `spec.{key}=значение` — текстовая характеристика (несколько значений — ИЛИ);
- `spec.{key}=true|false` — логическая характеристика;
- `spec.{key}.min`, `spec.{key}.max` — диапазон числовой характеристики;
- `sort` — `newest` (по умолчанию), `price_asc`, `price_desc`, `name`;
- `page`, `pageSize` (1–100, по умолчанию 20).

Некорректные параметры возвращают `400` с описанием ошибок по именам параметров.
Пустые значения (например, незаполненное поле формы) игнорируются.

### Административный API

Нужен bearer-токен пользователя с ролью `Admin` (`POST /api/auth/login`): без токена — `401`,
с токеном без роли (например, покупателя) — `403`.

| Метод и путь | Описание |
| --- | --- |
| `GET /api/admin/brands`, `GET /api/admin/brands/{id}` | Бренды с числом товаров |
| `POST /api/admin/brands`, `PUT /api/admin/brands/{id}`, `DELETE /api/admin/brands/{id}` | Создание, изменение, удаление бренда |
| `GET /api/admin/categories` | Плоский список разделов с `parentId` в порядке обхода дерева |
| `GET /api/admin/categories/{id}` | Раздел с его характеристиками |
| `POST /api/admin/categories`, `PUT /api/admin/categories/{id}`, `DELETE /api/admin/categories/{id}` | Создание, изменение и перенос раздела (`parentId`), удаление |
| `POST /api/admin/categories/{id}/specs` | Добавить характеристику: `key`, `name`, `unit`, `valueType` (`Text`, `Number`, `Boolean`), `isFilterable`, `sortOrder` |
| `GET`, `PUT`, `DELETE /api/admin/categories/{id}/specs/{specId}` | Получить, изменить, удалить характеристику |
| `GET /api/admin/products` | Товары, включая неопубликованные: `q` (название или артикул), `categoryId` (с подразделами), `brandId`, `published`, `page`, `pageSize` |
| `GET /api/admin/products/{id}` | Товар с характеристиками, изображениями и списком доступных ему характеристик |
| `POST /api/admin/products`, `PUT /api/admin/products/{id}`, `DELETE /api/admin/products/{id}` | Создание (неопубликованным), изменение, удаление товара |
| `PUT /api/admin/products/{id}/specs` | Заменить характеристики: `{"specs": {"power_w": 80, "bluetooth": true}}` |
| `PUT /api/admin/products/{id}/images` | Заменить изображения: `{"images": [{"url": "...", "alt": "..."}]}`, порядок сохраняется |
| `POST /api/admin/products/{id}/publish`, `POST /api/admin/products/{id}/unpublish` | Показать товар на витрине или скрыть |
| `GET /api/admin/orders?status=&q=&customerId=` | Заказы: фильтр по статусу и покупателю, поиск по номеру, телефону, email, имени; `page`, `pageSize` |
| `GET /api/admin/orders/{id}` | Карточка заказа с допустимыми следующими статусами (`nextStatuses`) |
| `PUT /api/admin/orders/{id}/status` | Смена статуса, тело `{ "status": "Confirmed" }` — см. [статусы](#корзина-и-оформление-заказа); покупателю уходит письмо |
| `GET /api/admin/customers?q=` | Зарегистрированные пользователи: поиск по email или имени, дата регистрации, число и сумма заказов (без отменённых); `page`, `pageSize` |
| `GET /api/admin/customers/{id}` | Карточка: роли, подтверждён ли email, блокировка входа, статистика заказов |
| `POST /api/admin/customers/{id}/unlock` | Снять блокировку входа после неудачных попыток |

Правила и ошибки каталога:

- slug — строчные латинские буквы, цифры и дефисы. Если его не передать, при создании он формируется из названия
  (кириллица транслитерируется: «Ламповий підсилювач» → `lampoviy-pidsilyuvach`), а при изменении остаётся прежним;
- цена и остаток не отрицательные, старая цена (если задана) больше текущей;
- ключ характеристики товара должен принадлежать разделу товара или его предкам, значение — подходить по типу.
  Ключи уникальны в ветке каталога (раздел, его предки и подразделы). При смене раздела у товара удаляются
  значения характеристик, которых нет у нового раздела;
- товар, который уже заказывали, удалить можно: позиции заказов — снимок (артикул, название, цена) без ссылки
  на товар и не меняются, а при отмене такого заказа остаток просто некуда вернуть. Чтобы убрать товар с витрины,
  но сохранить его в админке, снимите его с публикации;
- `400` — ошибки по полям (`errors.price`, `errors["specs.power_w"]`, `errors["images[0].url"]`), в том числе перенос
  раздела в самого себя или в свой подраздел;
- `409` — занятый slug или артикул; удаление бренда с товарами или раздела с подразделами или товарами; перенос раздела,
  после которого ключи характеристик в ветке повторяются; смена типа характеристики, у которой уже есть значения.

## Заявки на консультацию

Страница `/consultation` (английская — `/en/consultation`) принимает запросы на подбор системы,
изготовление на заказ, вопросы по товару и сервис. Входы — шапка и мобильное меню, подвал, блок на главной
и кнопка «Запитати майстра» в карточке товара (при нулевом остатке — «Хочу схожий»).
Ссылка `/consultation?product=<slug>` подставляет опубликованный товар, `?topic=CustomBuild` — тему.

`POST /api/inquiries` принимает:

```json
{
  "topic": "CustomBuild",
  "name": "Олена",
  "phone": "+380 67 123 45 67",
  "email": null,
  "preferredContact": "Telegram",
  "message": "Потрібен ламповий підсилювач для кімнати 20 м².",
  "budget": "до 80 000 ₴",
  "productSlug": "aurora-i-80",
  "consent": true
}
```

- Темы: `Selection`, `CustomBuild`, `Product`, `Service`, `Other`. Способы связи: `Phone`, `Telegram`,
  `Viber`, `Email`. Для почты обязателен email, для остальных способов — телефон (10–15 цифр).
- Обязательны имя (до 200 символов), описание (10–3000 символов) и согласие на обработку контактов.
  Бюджет — необязательный текст до 100 символов. Валидация на сервере, ошибки по полям — `400`.
- Ответ `201`: `{ "number": 1001 }`. Номер выдаёт последовательность PostgreSQL. С bearer-токеном
  заявка связана с аккаунтом; без токена или с просроченным токеном сохраняется как гостевая.
  Название и slug товара сохраняются снимком; неизвестный или неопубликованный товар не привязывается.
- Поле `website` — скрытая ловушка: заполнено — ответ об успехе без сохранения и писем.
  Лимит — 5 запросов за 10 минут на адрес, затем `429`. Лимит хранится в памяти процесса и использует
  первый `X-Forwarded-For` (или адрес соединения): его можно подделать, поэтому это базовое ограничение,
  а не замена защите от ботов на доверенном внешнем прокси.
- После сохранения письмо владельцу ставится в очередь, если задан `Store__OwnerEmail`, покупателю —
  если оставлен email. Реальная доставка подключается отдельно (см. «Почта»); по умолчанию письма только в логе.

Админка: `/admin/inquiries` — список, поиск по номеру, имени, телефону, email и тексту, фильтр по статусу
и страницы по 20 записей. `/admin/inquiry/{id}` — контакты, запрос, товар, бюджет, внутренняя заметка.
Статусы `New` → `InProgress` → `Closed`, также `Spam`; можно вернуть заявку в любой статус.
Заметки видны только администраторам, несохранённые изменения защищены предупреждением при уходе.
На обзоре — счётчик новых заявок со ссылкой на отфильтрованный список.

| Метод и путь | Описание |
| --- | --- |
| `GET /api/admin/inquiries` | Список: `status`, `q`, `page`, `pageSize` |
| `GET /api/admin/inquiries/{id}` | Карточка заявки |
| `PUT /api/admin/inquiries/{id}` | `{ "status": "InProgress", "adminNote": "Перезвонить" }`; пропущенные поля не меняются, пустая заметка очищает её |

Все административные endpoints требуют роль `Admin`. Миграция `AddInquiries` создаёт таблицу и
последовательность; применяется командой `migrate` или при `Store:AutoMigrate`.

## Корзина и оформление заказа

**Корзина** хранится в браузере (`localStorage`) и содержит только id товаров и количество. Названия, цены
и наличие витрина каждый раз берёт из `POST /api/cart/quote`, поэтому устаревшая цена в корзине не показывается.

**Оформление** — `POST /api/orders`:

```json
{
  "items": [{ "productId": "…", "quantity": 2 }],
  "fullName": "Иван Петров",
  "phone": "+380 67 123 45 67",
  "email": "ivan@example.com",
  "deliveryMethod": "NovaPoshtaWarehouse",
  "city": "Киев",
  "warehouse": "Отделение №12",
  "paymentMethod": "CashOnDelivery",
  "comment": "Позвоните перед отправкой"
}
```

- Способы доставки: `NovaPoshtaWarehouse` (нужны `city` и `warehouse`), `NovaPoshtaCourier` (`city` и `address`),
  `Pickup` (адрес не нужен). Лишние поля адреса отбрасываются. Необязательные `cityRef` и `warehouseRef` сохраняются
  для будущей интеграции со справочником Новой почты.
- Оплата: `CashOnDelivery` (при получении) или `BankTransfer` (по счёту). Онлайн-оплаты нет.
- Всё проверяется на сервере: товары опубликованы, количество от 1 до 99, телефон — 10–15 цифр (пробелы, скобки
  и дефисы убираются), формат email, обязательные поля для выбранной доставки. Ошибки — `400` с сообщениями
  на русском по именам полей (`fullName`, `items[0].quantity` и т. д.).
- Цены берутся только из каталога; цены и суммы от клиента игнорируются. Позиции сохраняются снимком
  (артикул, название, цена, количество, сумма) и не меняются, если товар потом изменят или удалят.
- **Остатки списываются атомарно.** В транзакции для каждой позиции выполняется
  `UPDATE "Products" SET "Stock" = "Stock" - @qty WHERE "Id" = @id AND "IsPublished" AND "Stock" >= @qty`.
  Строка товара блокируется: параллельный заказ ждёт и после фиксации перепроверяет условие уже на новом
  остатке, так что продать больше, чем есть, нельзя. Строки блокируются в порядке id — без взаимоблокировок.
  Если хоть одной позиции не хватило, транзакция откатывается и API отвечает `409` со списком
  `items: [{ productId, name, requested, available }]`.
- С bearer-токеном заказ привязывается к аккаунту. Просроченный или неверный токен даёт `401`, а не гостевой
  заказ, чтобы заказ не пропал из личного кабинета незаметно для покупателя. Роль для этого не нужна: оформлять
  заказы и смотреть свои заказы может любой вошедший пользователь, в том числе без роли `Customer`
  (например, созданный до того, как регистрация стала её назначать).
- Ответ `201`: `{ "token": "…", "order": { … } }`. Номер заказа (`100001`, `100002`, …) выдаёт последовательность
  PostgreSQL — он для общения с менеджером и доступа не даёт. Доступ к странице подтверждения
  (`/orders/{token}` на витрине) даёт только **публичный токен**: 256 случайных бит в base64url. В базе хранится
  лишь его SHA-256, поэтому ссылку нельзя ни подобрать, ни восстановить из базы.

**Статусы:** `New` → `Confirmed` → `Shipped` → `Completed`; из любого незавершённого статуса — в `Cancelled`
(для отправленного заказа это отказ при получении). Другие переходы — `409`. Отмена возвращает товары на склад
ровно один раз: смена статуса — условный `UPDATE … WHERE "Status" = <прежний>`, и из двух одновременных отмен
срабатывает только одна.

## Известные ограничения

- Роль `Admin` выдаёт только команда `create-admin` (в разработке — ещё и инициализатор из настроек `Seed:Admin`
  при `Store:AutoMigrate`). Админка показывает пользователей и умеет снимать блокировку входа, но менять роли
  в ней нельзя: снять роль `Admin` можно только в базе. Роли попадают в bearer-токен при выдаче, поэтому изменение ролей вступает в силу после
  повторного входа или `POST /api/auth/refresh`.
- Админ-панель (`/admin`, `/en/admin`) проверяет роль в браузере через `GET /api/account/me` (токен хранится
  в `localStorage`); защиту данных обеспечивает сам API (`401`/`403`). Если роль `Admin` выдали после входа, `/me` её
  уже видит, а токен ещё нет — админка попросит войти заново. Загрузки файлов нет: изображения товаров задаются адресами.
- На карточке товара для несуществующего slug страница показывает «не найдено», но HTTP-статус 200:
  при потоковом рендеринге (Cache Components) статус уже отправлен к моменту `notFound()`.
- Токен входа в фронте хранится в `localStorage` — для демо. Для продакшена лучше httpOnly-cookie.
- Заказы: нет онлайн-оплаты и расчёта стоимости доставки (в сумму заказа она не входит); город и отделение
  Новой почты вводятся текстом, справочника и проверки адреса нет.
- Ссылка на страницу подтверждения заказа приходит покупателю письмом сразу после оформления, но в базе хранится
  только хеш токена, поэтому в письмах о смене статуса гостю ссылки нет. Вошедший пользователь видит заказы в личном кабинете.
- Реальная отправка в шаблоне выключена (`Email:Provider=Log`). Очередь писем — в памяти процесса:
  письма, не отправленные до остановки API, теряются. Вход без подтверждённого
  email разрешён; восстановить пароль без подтверждённого email нельзя (так работает Identity).
- Пользователи, созданные до появления даты регистрации, показываются в админке без неё.
- Остаток списывается при оформлении: неподтверждённые заказы держат товар, пока менеджер их не отменит.
  Автоматической отмены «зависших» заказов нет.
- `PUT /api/admin/products/{id}` заменяет товар целиком, в том числе остаток (`stock` не передан — 0), а
  оптимистичной блокировки нет: если между загрузкой товара в админке и сохранением оформили заказ, сохранение
  вернёт остаток, который был до заказа, и проданный товар снова окажется «в наличии». Проверяйте остаток после правки.
- Нет ограничения частоты запросов на `POST /api/orders` и защиты от ботов.
- Корзина привязана к браузеру, а не к аккаунту: на другом устройстве она пустая.
- Даты на витрине показываются в часовом поясе `Europe/Kyiv` (константа в `web/lib/format.ts`).
